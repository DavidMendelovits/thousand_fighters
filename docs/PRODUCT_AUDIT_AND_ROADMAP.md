## The product we are building

Turn photos, paintings, and original concepts into distinctive playable fighters. Their movement should follow their material and anatomy: paint flows and reshapes; elastic bodies stretch; summons act independently. Do not force every concept into a human skeleton or identical move template.

The creation loop is: references and concept → character-specific move/input design → approved identity references → coherent video-derived motion → normalized animation and separate effects → collision/timing authoring → visual and gameplay review → versioned publication → play.

The workbench is the supported interface for that entire loop. The fighting game must be enjoyable in its own right, including on mobile. Every paid attempt and intermediate artifact should be traceable, and users should be able to branch or resume without needlessly regenerating.

### Important discrepancies and risks

1. **Engine capabilities exceed creation-schema capabilities.** The structured character event schema currently enumerates `hitbox_active`, `hitbox_end`, and `spawn_projectile`. It does not express the full summon/transformation vocabulary supported by runtime/config extensions. Generation cannot reliably invent advanced fighters through that contract alone.
2. **Telemetry is not yet an absolute accounting guarantee.** `emitAttempt` returns without a recorder and catches persistence failures. Main pipeline paths supply a recorder, but crash recovery, all direct callers, and durable intent-before-submission need explicit coverage. Unknown cost must remain unknown, never zero.
3. **Queue durability is absent.** Only the in-memory adapter is supported. Archived video jobs help recovery but do not replace durable orchestration, leases, cancellation, or restart reconciliation.
4. **Default provider selection is unsafe for production expectations.** With no configured provider, the image adapter uses a local placeholder. Codex and Gemini adapters remain selectable. Production must explicitly allow approved API providers and reject placeholders/subscription-only paths. This audit did not inspect secret values or establish the active deployed provider.
5. **History is not disaster recovery by itself.** Local immutable files are valuable, but manual cloud backup is not a tested recovery service. URL-only references may not preserve source bytes; legacy JSON-only versions cannot restore historical assets faithfully.
6. **Documentation contains stale claims.** Runtime gap metadata says roster export remains open although export exists. Roster loader comments promise built-in fallback despite an initially empty CMS-only roster. Reconcile docs and surface failed/empty roster loading clearly.
7. **Large uncommitted scope complicates releases.** The current working tree contains extensive modified and new files. A reviewable release checkpoint, asset strategy, and reproducible build are prerequisites to a trustworthy baseline.

- Structured creation and combo authoring can express controlled summons, real grabs/grip trajectories, held-direction commands, custom animation rows, and target/sky/behind projectile spawns.

- Added ten contract tests, including an isolated workbench HTTP create/save/reload round trip, custom-row generation/extraction acceptance, and an incomplete-pack export refusal. ### Implementation progress — September 19, component authoring and planning

CREATE-03 / CREATE-04 now have a usable workbench implementation, with full generated-character acceptance still open:

- Native summon editor: isolated actor description, lifetime, movement speed, spawn offsets and command. Adds recall and supports new controlled strikes/grabs with separate animation rows; preserves source moves and artwork. Exact command conflicts are rejected within each actor's controls.
- Native transformation editor: independent hidden child draft, its own art brief/moves/projectiles, timed or until-KO expiry and meter cost. No inherited body artwork. Open the child workspace, finish review, and explicitly install a snapshot into the parent. Legacy embedded forms are preserved, not silently migrated.
- Reviewed installation pins child provenance and copies required sprite/projectile bytes into a unique parent asset directory. Missing/unapproved/clipped motion and mixed-time assets block installation. Later child edits cannot change installed bytes. Parent checkpoints/export include installed form assets. Forms can own controlled summons too.
- Read-only animation plan lists required body, actor and linked-form rows with references, dependencies, extraction/review state and direct row/workspace navigation. Viewing the plan never submits generation or creates character versions. This is a planner, **not a durable background job queue**.
- Agent-browser exercised form creation, summon editing, controlled move creation, child/parent navigation, plan filtering and incomplete-install rejection in disposable keyless storage. Desktop and 390px mobile screenshots were inspected; error visibility and compact planning layout were adjusted. This did not validate new generated artwork or actual transformed gameplay.
- Verification: **70 focused tests passed**, TypeScript and syntax/diff checks passed. Keyless full-flow, row-generation, creation-kit (10 assertions) and combo-authoring (11 assertions) smoke tests passed. Updated the row smoke fixture to supply a draft for authored-row validation. Includes immutable export, concurrent-asset rejection, hidden-form publish refusal and summon-bearing form coverage. Fixture art is synthetic test data, not visual approval evidence.

See [the component authoring guide](CHARACTER_COMPONENT_AUTHORING.md). Remaining: full UI-to-generated-match recording (CREATE-07), effect/projectile coverage in the plan, full legacy-form migration, richer exit/control rules, automated generation-schema form planning, durable jobs/accounting, and visual validation of a newly created complete fighter. Independent form SFX packaging is not part of this slice.

Priorities: **P0** closes the creation-loop or safety gaps; **P1** makes the game enjoyable and the product usable; **P2** supports broader release and scale. They are priorities, not promised dates. Security gates become mandatory before any public CMS exposure.

## Decisions that should not be silently assumed

- **Online multiplayer:** scope is not established. Competitive networking requires its own simulation serialization, rollback, desync and matchmaking plan; local fixed-step timing alone is not netcode readiness.
- **Audience:** personal creator tool, invited creators, or public self-service changes permissions, moderation, billing and scale requirements.
- **Generation budgets:** choose per-character limits and approval thresholds before large benchmark batches.
- **Art direction:** maintain a shared readability/scale standard while permitting character-specific materials; do not erase painterly identity by applying a universal pixel filter.
- **First launch roster:** prefer a small completely reviewed set over treating every exported config as release quality.
- **Mobile delivery:** WebView is the current architecture. Decide whether measured limitations justify a different renderer only after real-device evidence.

## Recommended execution order

1. Establish coverage inventory, clean release baseline and reproducible checks.
2. Close schema/workbench gaps and guarantee paid-attempt recording and restart safety.
3. Create one new complex fighter through the UI; use failures to repair the general pipeline.
4. Complete and visually approve a small launch roster, then balance with real players.
5. Validate physical mobile devices and harden hosting/security before wider release.

Avoid expanding the roster or buying more motion batches until their acceptance and recovery workflows are reliable. A bigger pile of sprites is not automatically a bigger game.
